# Seller Cabinet AI

## О проекте

Seller Cabinet AI — веб-приложение личного кабинета продавца с интегрированным AI-помощником для работы с объявлениями.

Пользователь может:
- просматривать список своих объявлений;
- открывать страницу конкретного объявления;
- редактировать данные объявления;
- получать AI-подсказки для генерации / улучшения описания;
- получать AI-анализ ориентировочной рыночной цены.

## Настройка LLM (Ollama)

### 1. Установить Ollama

Установить Ollama на локальную машину.

### 2. Загрузить модель

Например, для проекта использовалась модель `llama3`:

```bash
ollama pull llama3
```

### 3. Проверить, что Ollama работает

Проверить доступность Ollama можно командой:

```bash
curl http://localhost:11434/api/tags
```

Если всё настроено корректно, Ollama вернёт JSON со списком доступных моделей.

Также можно проверить список моделей так:

```bash
ollama list
```

### 4. Адрес Ollama

По умолчанию backend ожидает, что Ollama доступна по адресу:

```text
http://localhost:11434
```

## Структура проекта

Проект состоит из двух частей:

- **client** — пользовательский интерфейс приложения;
- **server** — серверное API для работы с объявлениями и AI-роутами.

AI-запросы не отправляются в Ollama напрямую с клиента.  
client обращается к server, а server:
- валидирует входные данные;
- нормализует данные объявления;
- формирует prompt;
- отправляет запрос в Ollama;
- возвращает результат обратно в client.

Такой подход позволяет:
- не раскрывать внутреннюю prompt-логику на клиенте;
- централизованно управлять AI-функциями;
- проще заменять модель или дорабатывать поведение AI.

## Функциональность страниц

### 1. Список объявлений (`/ads`)
На странице списка реализовано:
- получение данных с сервера;
- поиск по названию;
- фильтрация по категориям;
- фильтрация объявлений, требующих доработки;
- сортировка;
- пагинация;
- два режима отображения: плитка и список;
- состояния загрузки, ошибки и пустого списка.

### 2. Просмотр объявления (`/ads/:id`)
На странице просмотра отображаются:
- название;
- цена;
- дата публикации;
- дата последнего редактирования;
- изображение-плейсхолдер;
- характеристики товара;
- описание;
- блок «Требуются доработки», если не заполнены некоторые поля.

Также доступны:
- переход к редактированию;
- возврат к списку объявлений.

### 3. Редактирование объявления (`/ads/:id/edit`)
На странице редактирования реализовано:
- загрузка данных существующего объявления;
- форма редактирования;
- динамический набор характеристик в зависимости от категории;
- обязательные поля с валидацией;
- подсветка пустых полей, требующих доработки;
- AI-помощник для описания и цены;
- сохранение изменений;
- отмена редактирования;
- сохранение черновика в `localStorage`.

---

## AI-функции

### Генерация / улучшение описания
На странице редактирования пользователь может:
- сгенерировать новое описание, если поле пустое;
- улучшить существующее описание, если оно уже заполнено.

AI формирует предложение на основе:
- категории;
- названия;
- описания;
- характеристик объявления.

Результат показывается пользователю как подсказка, после чего его можно применить в форму.

### Анализ ориентировочной рыночной цены
AI возвращает не одну цену, а ориентировочные диапазоны по нескольким сценариям

Это позволяет сделать оценку полезнее и реалистичнее.

### Отмена AI-запросов
При уходе со страницы редактирования незавершённые AI-запросы отменяются через `AbortController`.

Это сделано для того, чтобы:
- не обновлять уже неактуальный UI;
- не показывать ошибки после смены страницы;
- избежать лишней нагрузки.

---

## Работа с черновиком формы

Изменения на странице редактирования автоматически сохраняются в `localStorage`.

Поддерживаются следующие сценарии:
- восстановление несохранённых изменений после обновления страницы;
- использование черновика при повторном открытии формы;
- очистка черновика после успешного сохранения объявления.

## Описание принятых самостоятельных решений

### 1. Настройка CORS на backend

В процессе интеграции frontend и backend была доработана настройка CORS на сервере.

Изначально базовой настройки было недостаточно для корректной работы запросов на изменение данных, так как браузер отправляет предварительный `OPTIONS`-запрос (`preflight`) перед `PUT`-запросами. Из-за этого сохранение изменений из формы редактирования не проходило.

В рамках доработки CORS был настроен так, чтобы:
- frontend-приложение, запущенное локально, могло корректно обращаться к backend;
- сервер корректно обрабатывал preflight-запросы;
- запросы на чтение и изменение данных работали в едином сценарии без ошибок, связанных с политикой браузера.

Это решение было необходимо для полноценной локальной разработки и тестирования клиент-серверного взаимодействия.

### 2. Расширение контракта списка объявлений: добавление `id` в ответ `GET /items`

При интеграции страницы списка объявлений с backend было обнаружено, что эндпоинт `GET /items` возвращал только сокращённый набор данных по объявлениям:
- категория;
- название;
- цена;
- признак необходимости доработки.

Для frontend этого оказалось недостаточно, так как без `id` невозможно:
- корректно строить ссылки на страницу просмотра объявления;
- открывать страницу редактирования конкретного объявления;
- однозначно идентифицировать элементы списка.

Поэтому в обработчике `fastify.get<ItemsGetRequest>('/items', ...)` была доработана серверная логика так, чтобы вместе с остальными полями возвращался также `id` объявления.

Это решение позволило:
- привести серверный ответ в соответствие фактическим потребностям клиентского приложения;
- реализовать корректную навигацию между списком, просмотром и редактированием;
- использовать стабильные ключи при рендеринге элементов списка на frontend.

### 3. Хранение данных объявлений только в памяти текущего backend-сеанса

Backend в рамках тестового задания работает с данными объявлений без постоянного хранилища. Изменения применяются к данным в памяти текущего процесса, поэтому после перезапуска сервера состояние объявлений возвращается к исходному значению из тестового набора данных.

Это поведение было осознанно принято как допустимое в рамках текущего решения, потому что:
- основной фокус тестового задания — клиентская часть, UX и интеграция с AI;
- backend выступает как упрощённый mock / учебный API;
- для демонстрации сценариев просмотра, редактирования и сохранения данных этого достаточно;
- отсутствие постоянной записи в базу данных не мешает проверке основной логики приложения.

Таким образом, текущее поведение не является критичным ограничением для целей тестового задания, но в production-версии потребовалось бы полноценное постоянное хранилище.
